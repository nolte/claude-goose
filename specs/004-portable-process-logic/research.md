# Research: Portable Process Logic

**Feature**: `004-portable-process-logic` | **Date**: 2026-08-02

Phase 0 output. Every decision below was taken against material in this repository, and each names
what was read. Where something was not verified, it says so.

---

## R1 — What counts as the single source, and at what granularity

**Decision**: Split the host-neutral definition into three artifacts with distinct jobs:

| Artifact | Holds | Why separate |
|---|---|---|
| `process.md` | The stages: preconditions, outputs, completion conditions, verification | Already exists and is already host-neutral prose |
| `constraints.md` | The must-not-violate constraints, each with a stable id | Must be extractable by a machine, because bindings are rendered from it |
| `invocation-contract.md` | The named inputs and the obligations a binding must satisfy | Consumers currently cannot read it — see below |

**Rationale**: The constraints are the only part that has to be both human prose and machine input.
Giving them their own file with stable ids (`C-1` … `C-n`) makes extraction a line-range operation
rather than a parsing problem. Stages stay where they are; nothing about them needs to be rendered
into a binding.

The invocation contract is the sharper finding. It already exists as
`specs/001-goose-implementation-review/contracts/recipe-interface.md`, and it is good — it states
every parameter, its requiredness, its default, and the host rules it inherits. But it lives in the
spec tree, and `tests/goose-implementation-review/PORTABILITY.md` check 3 exists precisely because
consumers never receive that tree. So today the contract a consumer needs is the one thing they
cannot have. Moving a host-neutral copy into `process/` is not new authoring; it is relocating an
artifact to the side of the boundary it belongs on.

**Alternatives considered**:

- *One file holding stages and constraints together* — rejected: the renderer would have to know
  which prose is a constraint and which is a stage description, which is exactly the ambiguity that
  stable ids remove.
- *Constraints as YAML data* — rejected: they are normative prose that a human executes. Encoding
  them as data would optimise for the renderer at the cost of the reader, and the reader is the
  primary consumer under Principle I.

## R2 — How a constraint reaches the point of invocation

**Decision**: Bindings are **generated** from `constraints.md` and `invocation-contract.md`, committed
to the repository, and re-generated by the gate into a temporary location and compared. Any
difference fails the gate and names the artifact.

**Rationale**: This is the operator's decision, and the evidence behind it is specific. `O-12` in
`tests/goose-implementation-review/RESULTS.md` records a run pinned to baseline `2026-07-31` that
reported `2026-07-31b` and applied criteria which exist only in the newer revision. `--render-recipe`
proved the value arrived and that `instructions` contained the constraint verbatim; strengthening the
wording changed nothing, and a second run repeated the violation. Naming the pin in `prompt` fixed it
on the first attempt.

So a binding cannot be an empty pointer. "Minimal" has to mean *contributes nothing of its own*, not
*contains nothing*. Generation is what makes those two readings coincide: the binding is byte-for-byte
a function of the neutral source, so it cannot hold an opinion, and the gate proves it still doesn't.

**Alternatives considered**:

- *Bare pointer, re-measure whether `O-12` still bites* — rejected by the operator. It is the
  smallest artifact but it risks re-introducing a defect that took two failed runs to isolate.
- *Hand-copied preamble with a verbatim check* — rejected: same gate cost, but every rule change
  becomes one manual edit per binding, and the manual step is where drift enters.

## R3 — What the renderer is written in

**Decision**: POSIX shell plus `awk`. No Python, no templating engine, no package manifest.

**Rationale**: The renderer has to live inside `process/` rather than `scripts/`, because User Story 3
says a consumer writes a new binding without touching this repository's tooling. That puts it inside
the tree Principle I governs, and the tree's current runtime dependency set is *empty* — a consumer
needs Goose to run a review and nothing else to read one. Adding Python for a text-splicing job would
be the first dependency the reusable tree ever acquired, and it would be acquired for the maintainer's
convenience, not the consumer's benefit.

The work itself is modest: read a marked block, indent it, splice it into a template at a marker.
`awk` does this without ceremony.

**Verified**: `scripts/check-recipe-schema.sh` uses `bash` with an embedded `python3` heredoc and
`yaml`, so Python *is* available to the repository gate. The point is not availability; it is that
`process/` must not inherit the dependency.

**Alternatives considered**:

- *Python with PyYAML, matching the existing gate scripts* — rejected for the reason above. It would
  also mean the renderer round-trips YAML, which reformats comments; the Goose binding's comments
  carry findings worth keeping verbatim.
- *A templating engine* — rejected: a dependency, and a large one, for string substitution.

## R4 — Which host gets the second binding

**Decision**: Claude Code in headless mode (`claude -p`), rendered as a single executable shell file
per binding.

**Rationale**: Three properties were required: it must not be Goose, it must be executable here so
`FR-016` can actually be satisfied rather than claimed, and it must be a plausible thing for a
consumer to have. Claude Code satisfies all three, and there is a sharper reason: the current
documented invocation is `GOOSE_PROVIDER=claude-acp GOOSE_MODEL=default goose run --recipe …`. Goose
is already driving Claude. The second binding therefore removes a layer rather than adding a
different stack, which makes any difference between the two runs attributable to the binding and not
to a change of model.

**One authored file per binding** — a template — so `SC-004` holds literally once it counts
authorship rather than files on disk. It renders to `recipe.yaml` for Goose and to a shell file for
Claude Code that carries the rendered prompt in a heredoc and performs input substitution. An earlier
draft of this paragraph claimed one file per binding outright, which the template plus its rendered
output contradicts; the criterion was corrected rather than the count fudged. Host-specific glue is
permitted in a binding; rules are not.

**Alternatives considered**:

- *A human-only runbook* — rejected: it proves the artifacts are readable, not that they are
  sufficient. `FR-015` asks for an executable binding.
- *A third-party agent framework* — rejected: not installed here, so the run required by `FR-016`
  could not be performed, and an unexercised binding proves nothing.

## R5 — Where the executing host is recorded

**Decision**: In the report **header**, as a new field. The `DIGEST v1` block is left untouched.

**Rationale**: This follows directly from `FR-008`, and it is load-bearing. `report-template.md`
states the digest is "the ONLY part that must be byte-identical between two runs over unchanged
inputs", and Stage 6 of `process.md` classifies a delta over an identical `baseline=` and `subject=`
as a reproducibility failure rather than a change. Putting the host inside the digest would make every
cross-host comparison report a reproducibility failure by construction — the one comparison this
feature exists to enable would be the one it broke.

Keeping the digest at `v1` keeps the golden files under `tests/goose-implementation-review/expected/`
usable, since `RESULTS.md` `O-11` records that reconciliation is performed on the digest and never on
whole reports.

**Correction — the goldens are not left untouched.** An earlier version of this section said the
digest was unchanged and the goldens therefore stayed valid as they stood. The digest's first line is
`baseline=… process=<semver> subject=…`, so the bump to `2.0.0` rewrites `process=` in every report
from here on, and `recipe-clean.md:11` and `recipe-with-deviations.md:11` currently read
`process=0.2.0` — which also means they have been stale against `VERSION.md` `1.0.0` since the first
release. `VERSION.md` defines MAJOR as the bump that "invalidates existing golden files"; this is the
mechanism by which it does. The goldens are re-pinned once (T029) and every other digest field must
stay byte-identical. `FR-008` is unaffected — `process=` is a property of the process, not the host,
so it does not vary across hosts running the same version.

**Alternatives considered**:

- *`DIGEST v2` with a host field* — rejected for the reason above, and it would invalidate three
  golden files for no gain.
- *Recording the host only in the run log* — rejected: `FR-007` requires it in the report, and a
  report that cannot say what produced it fails Principle VI when it travels alone.

## R6 — Version impact on the process

**Decision**: `2.0.0`. MAJOR.

**Rationale**: `VERSION.md` defines MAJOR as "the parameter contract or report format changes in a
way that breaks existing consumers or invalidates existing golden files", and adds that on reaching
`1.0.0` the format is promised to consumers. The input names, requiredness and defaults are all
preserved (`FR-009`), and the digest is preserved (`R5`) — but the recipe moves from
`process/goose-implementation-review/recipe.yaml` to `process/goose-implementation-review/bindings/goose/recipe.yaml`,
and that path appears in every documented invocation. A consumer's command line stops working. That
is a break, and calling it MINOR because "only a path changed" would be exactly the kind of
convenient reading Principle VI rules out.

`VERSION.md` history must therefore state the old path, the new path, and what a consumer does about
it.

**Note on immutability**: the append-only rule that governs `baselines/goose/<revision>/` does **not**
apply to `process/`. `CLAUDE.md` scopes it to published baseline revisions, and `VERSION.md` scopes
process history to a changelog. Restructuring the process tree is permitted; doing it without a
version bump and a recorded reason is not.

**Alternatives considered**:

- *Keep `recipe.yaml` at its current path and bump to `1.1.0`* — rejected: it buys compatibility for
  a consumer set that is currently the author plus two recorded foreign-repository runs, and pays for
  it with an asymmetric layout where one host binding sits at the root and every other one lives in
  `bindings/`. User Story 3 is about the second binding being unremarkable to add.

## R7 — How the gate enforces the separation

**Decision**: One new local pre-commit hook, plus path updates to two existing ones.

| Hook | Change |
|---|---|
| `binding-render` (new) | Re-renders every binding and compares against the committed file. Default stage — needs only `sh` and `awk`, so it runs in the shared CI job |
| `recipe-schema` | `files:` and `entry:` follow the recipe to its new path |
| `recipe-parse` | Same; stays on the `manual` stage because it needs the `goose` binary |

**Rationale**: `.pre-commit-config.yaml` is the declared single source for checks and `CLAUDE.md`
forbids defining a check inline in a workflow, so the render check belongs there and reaches CI
through `task ci` unchanged. Keeping it off the `manual` stage matters: drift between a binding and
its source must fail on a workstation before a push, which is the whole argument for the gate.

`SC-002` ("zero normative statements appear in more than one artifact") is satisfied in two decidable
parts, not by one structural claim. An earlier draft of this section argued that a binding is *wholly*
generated and therefore cannot hold a hand-written rule. That is false, and the contract this feature
writes says so itself: `contracts/binding-render.md` marker rule 2 states that content outside a
marker pair belongs to the template and is never touched. Templates have non-generated regions by
construction.

So the failure mode is not someone inventing a rule out of nowhere — it is someone writing a rule into
a *template*, where the renderer reproduces it faithfully forever and the render check reports green.
`FR-018` and `FR-019` close it: every template line must sit in a declared region, and the only region
that is not generated may not be written in normative voice. Both are lexical and therefore decidable.

Detecting duplicated *meaning* across differently worded prose remains undecidable statically.
`OMISSIONS.md` records that rather than letting a passing gate imply otherwise — a check that passes
for the wrong reason is worse than an absent one, because it is reported as evidence.

## R8 — The portability guard is documented but not wired

**Verified**: `tests/goose-implementation-review/PORTABILITY.md` specifies a three-part static guard
(repository name, absolute paths, references to `specs/`). `.pre-commit-config.yaml` contains no hook
that runs it. It is a procedure a human is expected to remember.

**Also verified — it does not currently pass.** Running check 3's own expression,
`grep -rIn 'specs/[0-9]' process/ baselines/`, returns one hit: `baselines/SOURCE-FORMAT.md:7`,
"Governed by `specs/002-qa-documentation-base/data-model.md`, which is normative where the two
differ." A consumer copying `baselines/` receives a pointer to a document they do not have, and are
told it overrides the file they *do* have. Checks 1 and 2 return nothing. The fix belongs to this
feature (T011a) because wiring an already-failing check would otherwise turn the whole gate red on
content this feature did not write. The file is at the root of `baselines/`, not inside a published
revision, so the append-only rule does not protect it.

This is the third time the guard has been run and found something the moment it was actually
executed — `PORTABILITY.md` "Guard history" records the first two. That is the argument for wiring it
rather than documenting it, stated in evidence instead of in principle.

**Decision**: Implement it as `scripts/check-portability.sh` and add it to the gate as part of this
feature.

**Rationale**: `FR-011` requires the guard to cover every artifact this feature introduces, and this
feature introduces the first *executable* file in the reusable tree. A shell script is precisely where
an absolute path gets hard-coded during debugging. A guard that depends on someone remembering to run
it will not catch that. `PORTABILITY.md` itself records that the guard's own blind spot was once the
defect — a passing check with the wrong scope is more dangerous than none, "since it is reported as
evidence". The same argument applies to a check that is never invoked.

## R9 — A pre-existing inconsistency that must not be carried forward

**Verified**: `process.md` ends with a table titled "Stages not yet implemented" listing baseline
pinning, version-mismatch handling, offline behaviour and delta comparison as "Planned". All four are
implemented in the same file — Stage 3b covers the first three, Stage 6 the fourth — and `VERSION.md`
records them as shipped in `1.0.0`. The closing sentence, that a report "makes no claim that the
revision is current", contradicts Stage 3b's drift check.

**Decision**: Correct it during the migration. Not scope creep: the file is being restructured, and
carrying a known-false statement into a new revision would violate Principle VI in the act of
re-publishing it.

## R10 — Relationship to the proposed baseline criterion

**Verified**: `RESULTS.md` `O-12` proposes a criterion for a future baseline revision — *constraints
that must not be violated appear in `prompt`* — with evidence class `observed`, since no consulted
document states it.

**Decision**: This feature does not add that criterion. It makes the property structural for this
process's own bindings, and records the link so that whoever grows the baseline (feature `002`) finds
it.

**Rationale**: Baseline revisions are immutable once published and adding a criterion means publishing
a successor revision with its own sources, coverage and verification record. That is feature `002`'s
work, and folding it in here would mix two release units.

## Unresolved at the end of Phase 0

- **Whether two hosts produce identical digests over the same subject.** Deliberately open. `FR-017`
  requires the comparison to be run and every difference explained; it does not require agreement.
  The spec's Assumptions record why: `O-11` shows it took four rounds of specification to make the
  digest stable across runs on *one* host, so assuming agreement across two would be a claim without
  evidence.
- **Whether `claude -p` honours a constraint carried in its prompt as reliably as Goose does.** This
  is the `O-12` question asked of the second host. It cannot be answered by reading; the run required
  by `FR-016` answers it, and the answer is recorded either way.
